      Bean 생명주기

      초기화와 소멸직전 구간에서 초기화와 소멸직전구간에서 @PostConstruct와 @PreDestroy가 호출 된다

      • 생성: 생성자 호출 (아직 초기화되지 않음)
      • 주입: 생성자 주입이면 생성과 동시에 끝남
      • 초기화: @PostConstruct 실행 (의존성이 준비된 후)
      • 소멸: 컨테이너 종료 시 @PreDestroy 실행

      @PostConstruct 예시

      Service.java
      @Service
@RequiredArgsConstructor
public class BadWordFilter {

    private final PostProperties properties;
    private Set<String> words;

    @PostConstruct
    void prepare() {
        words = properties.getBadWords().stream()
                .map(w -> w.strip().toLowerCase(Locale.ROOT))
                .filter(w -> !w.isBlank())
                .collect(Collectors.toUnmodifiableSet());

        if (words.isEmpty()) {
            throw new IllegalStateException("board.post.bad-words 설정이 비어 있습니다.");
        }
    }
}

      다른 Bean을 건드릴 수 있으므로, 생성자에서 하는 초기화 작업은 지양하고 @PostConstruct에 두는 것이 좋음

      @PreDestroy 예시

      Service.java
      @Service
public class AsyncWorker {

    private final ExecutorService executor = Executors.newFixedThreadPool(4);

    @PreDestroy
    public void shutdown() {
        executor.shutdown();
    }
}

      쓰레드에서 빈이 제거되기 전에 호출해주는 코드인데…

      @PreDestroy는 사실상 쓸 일은 없다

      위의 코드도 사실상 설명을 하기 위한 예제일 뿐 이다

      빈 스코프(Bean Scope)

      new ()로 객체를 생성 안해줘도 되는 이유가 이 IoC Container 덕분이다 (제어 역전, IoC) 그 객체들을 Bean 이라 하고, 담겨있는 상자가 IoC 컨테이너, 빈을 사용하는 행위가 DI(의존성 주입)이다

      빈 라이프 사이클 4가지

      1. singleton: @Service, @Repository 등 기본값, 99.9999% 싱글톤만 씀
      2. prototype: 주입/조회 할 때 만 사용 (@Scope("prototype") 선언)
      3. request: HTTP 요청마다 재사용
      4. session: HTTP 세션마다 재사용

      순환 참조

      순환 참조 문제

      MemberService와 PostService가 서로를 주입받아 호출하면 무한 루프 발생

      순환 참조 해결

      MemberReader.cs
      @Service
@RequiredArgsConstructor
public class MemberReader {
    private final MemberRepository memberRepository;
}
      PostService.cs
      @Service
@RequiredArgsConstructor
public class PostService {
    private final MemberReader memberReader;
}

      둘 다 필요로 하던 코드를 제3의 클래스(MemberReader)로 꺼내서 사용하는 것이 해결책임

      잘못된 순환 참조 해결

      • spring.main.allow-circular-references=true로 덮기
      • 필드 주입(@Autowired)으로 바꿔 에러만 사라지게 하기
      • @Lazy로 한쪽 주입을 미루기

      AOP

      실질적인 비지니스 로직이 아닌 부수적인 것들은 밖으로 빼서 관리하자는 것

      build.gradle 설정 (AOP)

      • 과거 implementation 'org.springframework.boot:spring-boot-starter-aop' 했음
      • 요즘 implementation 'org.springframework.boot:spring-boot-starter-aspectj' 사용

      @Aspect

      ExecutionTimeAspect.cs
      @Slf4j
@Aspect
@Component
public class ExecutionTimeAspect {

    @Around("execution(public * com.example.board..service..*.*(..))")
    public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        try {
            return joinPoint.proceed();
        } finally {
            long tookMs = (System.nanoTime() - start) / 1_000_000;
            if (tookMs >= 100) {
                log.warn("느린 호출 {} — {}ms", joinPoint.getSignature().toShortString(), tookMs);
            }
        }
    }
}
      • JoinPoint: 끼워 넣을 수 있는 지점
      • Advice: 그 지점에서 할 일 (@Before, @After, @Around)
      • Pointcut: 어디에 적용할지 고르는 식

      AOP를 실제로 쓸 일은 거의 없지만 면접에서 가끔 물어보는 주제다

      프로퍼티 바인딩

      application.yml 등에 적힌 값을 자바 코드로 끼워 넣어주는 기능임

      @Value

      PostService.java
      @Service
public class PostService {
    private final int maxPostCount;

    public PostService(@Value("${board.post.max-count:3}") int maxPostCount) {
        this.maxPostCount = maxPostCount;
    }
}

      ${설정키:기본값} 형식으로 사용함

      @ConfigurationProperties

      PostProperties.java
      @ConfigurationProperties(prefix = "board.post")
@Validated
@Getter
public class PostProperties {
    @Min(1) private final int maxCount;
    // ...
}

      @EnableConfigurationProperties와 묶어서 클래스를 빈으로 등록해 DI 받아 씀

      프로필별로 프로퍼티 설정 방법

      프로필은 실행 환경에 따라 다른 설정을 선택할 때 사용함 공통값은 application.properties에, 로컬 환경에서 바꿀 값은 application-local.properties에 둠 local 프로필을 활성화하면 같은 위치의 공통 파일보다 로컬 전용 파일의 값이 우선함

      SPRING_PROFILES_ACTIVE=local 또는 실행 인자 --spring.profiles.active=local로 활성화함 파일을 만들기만 해서는 해당 프로필이 선택되지 않음

      application.properties
      # application.properties (공통)
spring.jpa.hibernate.ddl-auto=validate
logging.level.root=INFO
      application-local.properties
      # application-local.properties (로컬 전용)
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
logging.level.com.example.board=DEBUG
      application-test.properties
      # application-test.properties (테스트 전용)
spring.datasource.url=jdbc:h2:mem:test;MODE=MySQL
spring.jpa.hibernate.ddl-auto=create-drop

      프로필로 빈 등록 여부도 정할 수 있음

      샘플 데이터를 넣는 초기화 빈에 @Component와 @Profile("local")을 붙이면 local 프로필을 활성화했을 때만 등록됨

      실행 환경의 이름이 아니라 실제 활성 프로필을 기준으로 판단함

      HelloService.java
      @Service
@Profile("hello") // application-hello.properties 사용
public class HelloService{
    
}
