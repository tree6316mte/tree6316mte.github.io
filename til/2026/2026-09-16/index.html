      심화 프로젝트에 대한 발제가 시작 됬다...

      오늘은 심화 프로젝트에 대한 발제가 나왔습니다.

      그리고 동시성과 락에 대한 실시간 강의도 들었습니다.

      심화 프로젝트 발제

      실시간 게임의 서버 구현

      오늘부터 9월 22일(화)까지 총 7일간 진행되는 ‘실시간 게임의 서버 구현’ 개인 과제 발제가 시작되었습니다. 이번 과제는 단순한 REST API 구현을 넘어서, 실시간 양방향 통신과 대용량 트래픽 상황에서의 데이터 정합성까지 고려해야 하는 상당히 수준 높은 프로젝트입니다.

      필수 기술 스택 아키텍처 조건

      • 아키텍처: Controller, Service, Repository로 이어지는 표준 3-Layer Architecture를 준수해야 합니다.
      • 연관관계 매핑: 복잡도를 낮추기 위해 JPA 엔티티 간의 연관관계는 반드시 단방향으로만 설정해야 합니다.
      • 인프라: Docker를 활용하여 MySQL과 Redis를 필수적으로 구축하여 사용해야 하며, 타 DB(Oracle 등)는 허용되지 않습니다.
      • API 규격 준수: 제공된 API 명세서(JSON 필드, Enum 값, 엔드포인트 경로 등)를 정확히 일치시켜야 합니다.
      • 테스트 주도 검증: Lv 1, 2를 제외한 모든 과제(Lv 3 ~ 19)에 대해 이미 테스트 코드가 제공되어 있습니다. 개발자는 본인이 작성한 코드가 이 테스트를 무사히 통과하는지 스스로 검증하며 개발을 진행해야 합니다.



      동시성과 락 특강

      동시성 문제

      웹 서비스가 성장하여 동시 접속자가 많아지면 필연적으로 직면하는 문제가 바로 동시성 문제입니다. 가장 대표적인 예시로 재고 차감을 들 수 있습니다. 창고에 재고가 1개만 남은 상품을 두 명의 유저가 동시에 구매 요청을 보낼 경우, 서버가 데이터를 읽고(조회) 차감(수정)하는 그 짧은 찰나에 요청이 겹치면서 1개의 재고로 2명에게 판매가 완료되어 버리는 치명적인 데이터 정합성 훼손이 발생합니다.

      스프링(Spring) 프레임워크 기반 환경에서는 애플리케이션의 핵심 로직을 담당하는 @Service 클래스가 주로 싱글톤(Singleton) 빈으로 관리됩니다. 이로 인해 여러 스레드가 동시에 하나의 자원(상태)에 접근할 경우 동시성 버그가 아주 쉽게 발생할 수 있습니다.

      특히 이러한 문제는 트래픽이 몰리는 실제 운영(Production) 환경에서만 간헐적으로 터지기 때문에, 개발자의 로컬 단일 스레드 테스트 환경에서는 재현조차 매우 까다롭습니다.



      동시성 문제를 해결하는 3가지

      데이터의 정합성을 지키기 위해 우리는 자원에 자물쇠(Lock)를 걸어야 합니다. 상황에 따라 적절한 락 기법을 선택하는 것이 백엔드 엔지니어의 핵심 역량입니다.

      1. 애플리케이션 락 (synchronized)

      자바 애플리케이션 단에서 synchronized 키워드 등을 사용해 오직 한 번에 하나의 스레드만 특정 메서드나 블록에 접근하도록 통제하는 직관적인 방법입니다.

      • 한계점: 한 스레드가 작업하는 동안 다른 스레드들은 무작정 대기해야 하므로 시스템 전체의 처리량(Throughput)이 급격히 떨어집니다. 또한, 서버 인스턴스가 여러 대로 늘어나는 분산 환경(Scale-out)에서는 애플리케이션 락만으로 다른 서버의 접근을 통제할 수 없다는 치명적인 단점이 있습니다.

      2. 비관적 락 (Pessimistic Lock)

      “동시성 충돌이 반드시 발생할 것이다"라고 비관적으로 가정하고, 데이터베이스(DB) 수준에서 해당 데이터(Row)에 아예 강력한 자물쇠(Exclusive Lock 등)를 걸어버리는 방법입니다.

      • 장단점: 충돌 빈도가 매우 높을 것으로 예상되는 환경에서는 데이터의 안전성을 확실히 보장할 수 있습니다. 하지만 DB의 자원을 직접 잠그기 때문에, 병목 현상이 발생하여 시스템 전반의 대기 시간이 길어질 위험이 큽니다.

      3. 낙관적 락 (Optimistic Lock)

      “동시성 충돌이 자주 발생하지 않을 것이다"라고 낙관적으로 가정하는 방식입니다. 실제로 DB에 락을 거는 대신, 데이터 테이블에 @Version 컬럼을 두고 데이터를 읽은 시점과 수정하는 시점의 버전 번호를 비교합니다. 만약 그사이 누군가 데이터를 수정하여 버전이 달라졌다면 예외를 발생시킵니다.

      • 장단점: DB 락을 잡지 않으므로 충돌이 적은 상황에서는 성능이 매우 뛰어납니다. 하지만 막상 충돌이 발생했을 때는 실패한 요청을 처음부터 다시 실행하는 재시도(Retry) 로직을 애플리케이션 단에서 개발자가 직접 꼼꼼하게 구현해야 합니다.



      데드락(Deadlock) 방지

      락을 사용할 때 가장 주의해야 할 재앙은 바로 서로 다른 두 스레드가 락을 엇갈리게 쥐고 영원히 상대를 기다리는 **데드락(교착 상태)**입니다.

      데드락을 예방하기 위해서는 애플리케이션 전반에 걸쳐 락을 획득하는 순서를 항상 한 방향으로 일관되게 통일해야 합니다. 또한, 락을 요청할 때 무한정 기다리지 않도록 타임아웃(Timeout)을 설정하여 일정 시간 후에는 락 획득을 포기하고 예외를 뱉도록 안전장치를 설계하는 것이 중요합니다. 동시성 제어는 스레드와 컨테이너의 동작 원리를 깊이 이해할수록 더욱 견고하고 효율적으로 설계할 수 있습니다.
