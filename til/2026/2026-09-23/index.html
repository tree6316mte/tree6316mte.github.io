      2026년 9월 23일

      팀원 바뀌고 이제 클라이언트도 고려해야하고 강의는 2개 있고...

      시작한지 18일차에? 최종 프로젝트를 시작합니다…

      최종 프로젝트 요약

      진행 단계 요약

      • 10/2 클라이언트 MVP 시연

      • 10/6 서버 기획 및 설계(ERD/데이터 모델, API 명세)

      • 10/13 서버 구축 및 클라이언트 연동

      • 10/15 핵심 게임 기능 통합

      • 10/19 완성도 점검 및 자율 고도화 (필수 기능이 안정화된 팀만)

      • 10/21 최종 검증·문서화·발표 준비 → README, 발표회 브로셔, 결과 보고서, 시연 영상



      1. 최종 프로젝트 로드맵 및 핵심 목표

      정해진 상용 게임을 똑같이 베끼는 것이 아니라, 팀이 선택한 게임의 ‘핵심 재미’를 정의하고 이를 클라이언트와 서버를 거쳐 일관되게 동작하도록 설계 및 구현하는 것이 이번 프로젝트의 주된 목표입니다.

      • 핵심 플레이 루프: ‘플레이 -> 결과/보상 -> 성장/수집/강화 -> 다음 도전’으로 순환하는 명확한 루프가 존재해야 합니다.
      • 1~3주차 (MVP 및 서버 연동): 1주차에는 서버 없이도 임시 에셋과 UI만으로 플레이 가능한 클라이언트 MVP(Minimum Viable Product)를 완성해야 합니다. 2주차부터는 로컬 데이터를 서버 데이터로 전환하여, 재접속 시에도 상태가 유지되도록 연동합니다. (서버가 게임 데이터의 최종 기준점이 됩니다.)
      • 4~5주차 (안정화 및 고도화): 필수 기능이 안정화된 팀에 한하여, 새로운 기능 추가보다는 오류 수정, 통합 검증, 사용성 개선, 문서화(README, 기획서 등)에 집중하여 완성도를 끌어올려야 합니다.
      • 유의사항: 기존 상용 게임의 그래픽, 음원, IP 등을 무단 도용해서는 안 되며, 레퍼런스의 핵심 시스템만 참고하여 팀만의 테마로 재해석해야 합니다.



      2. 백엔드 인프라 및 운영 기술 (Spring 심화)

      이번 프로젝트 기간 동안 병행하여 적용해야 할 서버 및 인프라 학습 범위입니다.

      • AWS 기반 클라우드 구축: 공동 책임 모델과 IAM(최소 권한의 원칙)을 이해하고, VPC, 서브넷, 보안 그룹을 설정하여 EC2 인스턴스 환경을 구축합니다.
      • 운영형 Spring Boot: Actuator 라이브러리를 통해 애플리케이션의 상태와 지표를 점검하고 엔드포인트 접근을 제한합니다. Profile로 환경별 설정을 분리하며, AWS Parameter Store를 활용해 민감한 설정값을 관리합니다.
      • 데이터 관리: 파일 저장을 위한 S3, 관계형 데이터를 위한 RDS(MySQL), 캐싱과 세션 유지를 위한 Redis(ElastiCache)를 연동합니다.
      • 배포 자동화 (CI/CD): Dockerfile을 작성하여 애플리케이션을 컨테이너화하고, GitHub Actions와 AWS ECR을 연동하여 테스트, 빌드, 이미지 업로드 및 배포를 자동화합니다.



      3. 프로젝트 팀 협업 및 행정 유의사항

      • 소통과 기록: 회의 내용을 반드시 문서화하고, 팀원 모두가 동일한 이해를 바탕으로 개발하고 있는지 지속적으로 점검해야 합니다.
      • 팀프로젝트 지원금: 1인당 세후 약 39,000원의 지원금이 지급되며, 총무 1명이 서버 비용 등을 선결제하고 영수증으로 정산하는 방식입니다. (기타소득으로 잡혀 실업급여 수급에 지장이 있을 수 있으므로 대표 신청자를 신중히 선정해야 합니다.)
      • 출결 관리: 프로젝트 기간 동안 입/퇴실 체크가 누락되지 않도록 각별히 주의합니다.



      1. Spring AOP (Aspect Oriented Programming) 핵심

      AOP는 애플리케이션 여러 곳에서 반복되는 공통 기능(횡단 관심사, Cross-cutting Concerns - 예: 로깅, 트랜잭션, 시간 측정 등)을 핵심 비즈니스 로직에서 분리하여 모듈화하는 프로그래밍 기법입니다. 이를 통해 비즈니스 코드에 로그나 트랜잭션 코드를 단 한 줄도 넣지 않고도 해당 기능들을 수행할 수 있습니다. (마치 횡단보도처럼 여러 메서드를 가로지르는 공통 로직을 적용하는 방식입니다.)

      • 프록시(Proxy)의 역할: 자바는 컴파일 언어이기 때문에 실행 중에 원본 코드를 수정할 수 없습니다. 따라서 @Transactional 같은 AOP 기능을 적용하기 위해 스프링은 원본 코드를 감싸는 대리 객체(Proxy)를 생성합니다. 즉, 스프링이 프록시를 통해 트랜잭션을 시작(tx.start())하고 원본 코드를 호출(joinPoint())한 뒤 커밋 또는 롤백(tx.rollback())을 수행합니다. 프록시를 거치지 않으면 AOP가 동작하지 않습니다.
      • Weaving(위빙): 타겟 객체에 Advice(부가 기능)를 적용하는 과정을 ‘짜다(Weave)‘라는 의미의 Weaving이라고 부릅니다. (게임 ‘테일즈위버’가 ‘이야기를 짜는 사람’이라는 뜻인 것과 일맥상통합니다.)

      주요 용어 정리

      • Aspect: 횡단 관심사를 모듈화한 것 (Advice + Pointcut)
      • Advice: 실행할 부가 기능 코드와 그 실행 시점 (예: @Before, @Around)
      • Pointcut: Advice를 적용할 대상을 고르는 조건식
      • JoinPoint: Advice가 적용될 수 있는 지점 (스프링은 항상 ‘메서드 실행 시점’만 지원)
      • Target: Advice가 적용되는 실제 원본 객체
      • Proxy: Target을 감싸서 Advice를 대신 실행해주는 객체



      2. AOP 구현 실습 (Execution vs Annotation)

      AOP를 특정 메서드에 적용하는 방식은 크게 두 가지로 나뉩니다.

      • Execution 표현식 방식: execution(* com.spring.aop.execution.controller..*(..))와 같이 반환 타입, 패키지 경로, 클래스, 메서드 파라미터 등을 명시하여 원하는 계층(Controller, Service, Repository)의 메서드 호출 전후에 공통 로그를 찍도록 설정할 수 있습니다.
      • 어노테이션 기반 방식: @LogExecutionTime과 같은 커스텀 어노테이션을 직접 정의하고, AOP 설정에서 @Around("@annotation(com.spring.aop.config.LogExecutionTime)")로 잡아줍니다. 이후 측정하고 싶은 메서드 위에 해당 어노테이션만 붙이면 깔끔하게 실행 시간을 로깅할 수 있습니다.



      3. Filter (필터)의 역할과 동작 원리

      Filter는 AOP와 유사하게 공통 로직을 처리하지만, 동작하는 계층과 스펙이 다릅니다. Filter는 Spring의 기본 스펙이 아닌 서블릿(Servlet) 스펙이며, Spring의 DispatcherServlet에 요청이 도달하기 전 최전방에서 요청(URL 단위)을 가로채어 처리합니다.

      • OncePerRequestFilter: 요청 1번당 정확히 1번의 실행을 보장하는 스프링 제공 추상 클래스입니다.
      • 흐름 제어: filterChain.doFilter()를 기준으로 윗부분이 Controller 호출 전(Request 처리), 아랫부분이 Controller 호출 후(Response 처리)의 로직이 됩니다.
      • 등록 방식: @Component로 등록하면 모든 URL에 적용되고, 특정 URL에만 적용하려면 FilterRegistrationBean을 사용해 addUrlPatterns("/filter/*")를 지정합니다.



      1. Git 기본 개념 및 원리

      Git 환경은 크게 내 컴퓨터 내부의 ‘로컬(Local) 저장소’와 외부 서버에 위치한 ‘리모트(Remote) 저장소’로 나뉩니다. 코드가 이동하는 4단계(작업 디렉터리, 스테이징 영역, 로컬 저장소, 리모트 저장소)를 이해하는 것이 중요합니다. (참고로 리모트 저장소는 GitHub 외에도 GitLab, BitBucket 등 다양한 서비스가 존재하며, 기업의 상황에 따라 비용 효율적인 대안을 선택하기도 합니다.)

      리모트 저장소와 통신하는 주요 명령어의 차이는 다음과 같습니다.

      • git fetch: 리모트 저장소의 최신 작업 이력을 로컬로 가져오기만 하고, 현재 내 코드와 병합(Merge)하지는 않습니다. 변경 사항을 안전하게 확인만 하고 싶을 때 사용합니다.
      • git pull: 리모트의 내역을 가져온 뒤(fetch), 현재 작업 중인 로컬 브랜치의 코드와 즉시 병합(merge)하는 작업까지 한 번에 수행합니다.
      • git push: 로컬 저장소에 커밋(Commit)한 내역을 리모트 저장소로 업로드합니다.



      2. 실무적인 커밋(Commit) 컨벤션

      협업 시 커밋 메시지는 동료가 작업 내역을 한눈에 파악할 수 있도록 직관적이고 규칙적으로 작성되어야 합니다. 단순히 “좋은 코드다” 혹은 “수정 완료"와 같은 메시지 대신, 명확한 접두사를 사용하는 것이 표준입니다.

      • feat: 새로운 기능 추가
      • fix: 버그 수정
      • docs: 문서 수정
      • style: 코드 포맷팅, 세미콜론 누락 수정 등 (로직 변경 없음)
      • refactor: 코드 리팩토링 (기능 변화 없이 구조 개선)
      • test: 테스트 코드 추가 및 수정
      • chore: 빌드 프로세스, 패키지 매니저 설정 등 변경

      일부 취업 준비생이나 초보 개발자들 사이에서 커밋 메시지에 이모지(Gitmoji)를 넣는 경우가 있으나, 이는 실무 환경에서 비전문적으로 보일 수 있으며 검색 및 관리가 번거로워지므로 지양하는 것이 좋습니다.



      3. Issue 및 PR (Pull Request) 관리

      기능을 개발하거나 버그를 수정할 때는 코드를 먼저 짜는 것이 아니라, ‘이슈(Issue)‘를 먼저 등록하고 이를 해결하기 위한 ‘PR(Pull Request)‘을 올리는 것이 정석입니다.

      예약어를 통한 자동화

      커밋 메시지나 PR의 본문에 Closes #123, Fixes #45, Resolves #10과 같이 작성해 두면, 해당 PR이 기본(Default) 브랜치에 병합(Merge)되는 순간 연결된 이슈가 자동으로 닫힙니다. (대소문자는 구분하지 않습니다.)

      템플릿(Template) 활용

      팀원들이 일관된 양식으로 이슈와 PR을 작성하도록 강제하려면 템플릿을 활용해야 합니다. 프로젝트 루트 경로에 .github/ISSUE_TEMPLATE/bug_report.md 등의 마크다운 파일을 생성해 두면 GitHub가 이를 자동으로 인식합니다. 버그 리포트 시에는 재현 방법과 기대 동작을 적도록 유도하고, PR을 올릴 때는 콘솔 로그 제거 여부나 코딩 컨벤션 준수 여부를 체크리스트 폼으로 만들어 관리하면 코드 리뷰의 효율이 극대화됩니다.



      4. 팀 협업을 위한 Organization 및 브랜치 전략

      팀 프로젝트를 진행할 때는 개인 계정의 저장소보다는 무료로 제공되는 Organization을 생성하여 사용하는 것이 권장됩니다. 클라이언트와 서버 등 저장소가 여러 개로 나뉘더라도 같은 Organization 내에 두어 응집력을 높여야 합니다.

      권한 및 멤버 관리

      Organization 내에 프로젝트 저장소를 만든 뒤, 팀(Team)을 구성하여 멤버를 초대해야 합니다. 단순히 ‘Member’로 초대하면 쓰기(Write) 권한이 없으므로 코드를 푸시할 수 없습니다. 역할에 맞게 명시적으로 권한을 부여해야 합니다.

      브랜치 및 PR 워크플로우

      • 기본 브랜치 변경: 제품이 배포되는 main 브랜치 대신, 일상적인 개발이 모이는 dev 브랜치를 Default 브랜치로 설정합니다.
      • Feature 브랜치: 작업자는 dev 브랜치에서 분기하여 feat/login과 같은 피처 브랜치를 생성해 작업합니다.
      • PR 및 피드백 반영: 작업 완료 후 git push origin {브랜치명} 명령어로 푸시하고 PR을 생성합니다. 만약 리뷰어가 코드 수정을 요청하면, 새로운 PR을 만들 필요 없이 해당 브랜치에서 코드를 수정하고 다시 커밋 및 푸시하면 기존 PR에 자동으로 업데이트됩니다.
      • Git은 모든 히스토리를 남기기 때문에, 편법이나 조작된 커밋 역사 역시 그대로 남게 되므로 정석적인 흐름을 타는 것이 중요합니다.
