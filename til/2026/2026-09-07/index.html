      금토일 푹 쉬다 오니까 더 힘든 것 같은 하루였다…

      왜냐하면 금요일에 Spring 입문1,2가 추가되었기 때문…!

      금토일을 연달아 쉬었더니 엄청난 위기가 찾아온 것 이다

      그래서 원래 한번씩은 따라해보는데, 중간부터 강의를 한번 훑어보는 것으로 대체했다

      Docker 기초

      • Image (이미지) : 굽는다 (바꿀 수 없는 Read-Only 상태). 애플리케이션 실행에 필요한 환경, 코드, 라이브러리를 모두 모아둔 템플릿
      • Container (컨테이너) : 실행된 프로그램. 구워진 ‘이미지’를 바탕으로 메모리에 올라가 실제로 동작하는 격리된 프로세스

      Dockerfile 작성 및 빌드

      프로젝트 최상단에 Dockerfile이라는 이름으로 파일을 만들고 아래와 같이 작성했다

      # 1. 베이스 이미지 지정 (자바 21 버전)
FROM eclipse-temurin:21-jdk-alpine

# 2. 작업 디렉토리 설정 (컨테이너 내부 기준)
WORKDIR /app

# 3. 빌드된 JAR 파일을 컨테이너로 복사
COPY build/libs/*.jar /app/myapp.jar

# 4. JAR 파일 실행 명령어 설정
ENTRYPOINT ["java", "-jar", "/app/myapp.jar"]

      도커 이미지 빌드 (굽기)

      터미널에서 Dockerfile이 있는 경로로 이동한 뒤 아래 명령어를 실행한다

      # 현재 폴더(.)의 Dockerfile을 기반으로 'test-docker-hello'라는 이름(-t)의 이미지 생성
docker build -t test-docker-hello .

      Docker로 MySQL 띄우기

      백그라운드에서 MySQL 컨테이너를 실행하고 호스트와 포트를 연결한다

      # -d : 백그라운드 실행
# -p 3306:3306 : 호스트의 3306 포트와 컨테이너의 3306 포트 연결
# -e : 환경변수 설정 (루트 비밀번호 지정)
docker run -d --name mysql -e MYSQL_ROOT_PASSWORD=12345678 -p 3306:3306 mysql:8.4

      💡 팁 (볼륨 마운트와 영속성) 도커 컨테이너를 삭제하면 내부 데이터도 함께 날아가기 때문에, DB 데이터를 영구적으로 보존(영속성 유지)하려면 -v 옵션을 사용해 호스트 컴퓨터의 폴더와 연결해 주어야 한다


      자주 쓰는 도커 & 유용한 명령어 

      # 실행 중인 도커 컨테이너 목록 확인
docker ps

# 중지된 것을 포함한 모든 도커 컨테이너 목록 확인
docker ps -a

# 특정 컨테이너의 로그(출력 내용) 확인
docker logs [컨테이너명_또는_ID]

# 실행 중인 컨테이너 중지 및 삭제
docker stop mysql
docker rm mysql

# (참고) 특정 포트를 사용 중인 프로세스 찾아 강제 종료 (Mac/Linux)
kill -9 $(lsof -t -i:포트번호)

      JPA

      JPA는 SQL을 직접 쓰지 않고 객체만 다뤄도 DB 작업이 되게 해주는 ORM 중 하나이다


      Entity

      DB 테이블과 1:1로 매핑되는 객체 (JPA가 관리함)

      관련 어노테이션으로는 @Entity, @Table, @Id, @GeneratedValue, @Column이 있고

      매핑은 해당 느낌으로 작성된다

      CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    address VARCHAR(255)
);

      위의 SQL 문이 아래 Spring 구문으로 바뀐다

      @Getter
@Entity
@Table(name = "users")
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class User {

		@Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(length = 50, nullable = false)
    private String name;
    @Column(unique = true, nullable = false)
    private String email;
    private String address;
}

      JPA가 내부적으로 Entity 객체를 생성할 때 기본 생성자를 활용하기 때문에 @NoArgsConstructor는 꼭 붙혀줘야 한다

      Entity 클래스 코드 작성시 필수 

      @Getter
@Entity
@Table(name = "xxx")
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Xxx {

		@Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
		private Long id;
		// ...   
}

      Entity 클래스 작성 시 이렇게 6개는 무조건 적고 시작하면 좋다

      DB 및 JPA 설정 (application.properties) 

      # MySQL 데이터베이스 연결 정보
spring.datasource.url=jdbc:mysql://localhost:3306/{데이터베이스명}?serverTimezone=Asia/Seoul
spring.datasource.username=root
spring.datasource.password=12345678
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver

# JPA(Hibernate) 주요 설정
# ddl-auto 옵션: create(실행 시 기존 테이블 삭제 후 새로 생성), update(변경된 스키마만 적용), none(아무것도 안 함)
spring.jpa.hibernate.ddl-auto=create

# DB에 맞는 SQL을 생성하도록 방언(Dialect) 설정
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.MySQLDialect

# 실행되는 SQL 쿼리를 콘솔에 보기 좋게 출력
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

      계층 구조 (3-Tier Architecture)와 어노테이션

      스프링은 역할을 분리하여 유지보수를 쉽게 하기 위해 3계층 구조를 사용한다

      각 계층을 담당하는 클래스 위에는 알맞은 어노테이션을 붙여준다

      Spring에서 폴더 만들 때, 아래와 같은 5개의 폴더로 나눠주면 좋다


      • Controller Layer (@Controller / @RestController)
        • 클라이언트(사용자)의 HTTP 요청을 받고, 응답을 반환하는 커뮤니케이션 계층(url 매핑)
      • Service Layer (@Service)
        • 애플리케이션의 핵심 로직(비즈니스 로직)이 수행되는 구역 (데이터 가공, 트랜잭션 처리 등)
      • Repository Layer (@Repository)
        • 데이터베이스에 직접 접근하여 쿼리를 수행하고 데이터를 가져오는 계층

      DTO와 Entity

      • DTO (Data Transfer Object): 클라이언트(웹 브라우저)에게 데이터를 전달하기 위해 만든 전용 객체
      • Entity: DB의 Table과 1:1로 매핑되는 객체

      영속성 컨텍스트

      JPA가 엔티티를 관리하는 임시 저장소

      Entity의 생명주기

      비영속 : DB에 한번도 갔다오지 않은 상태 영속 : DB를 갔다 온 상태

      @Transactional

      여러 작업을 하나의 단위로 묶어서 모두 성공하거나 모두 실패하게 하는 것 (원자성)

      여러 개의 데이터베이스 연산을 하나의 논리적 단위로 묶어주는 것이 바로 트랜잭션이며, 이 논리적 단위의 기준이 되는 것이 바로 Service Layer에서 정의하는 비즈니스 로직

      @Transactional 속성

      속성 중 propagation, isolation, rollbackFor 은 입문 주차에서는 배우지 않는다

      • readOnly : true 설정 시, 읽기 전용으로 사용하여 성능을 최적화 (CUD 작업 불가)
      • propagation : 트랜잭션 전파 규칙을 정의 (e.g., REQUIRED, REQUIRES_NEW)
      • isolation : 트랜잭션의 격리 수준을 설정하여 동시성 문제를 제어
      • rollbackFor : 특정 예외가 발생했을 때 강제로 롤백하도록 지정

      JpaRepository

      JpaRepository를 사용하면 쿼리를 작성하지 않고도 쉽게 DB에 데이터를 CRUD 할 수 있다

      JpaRepository 사용예시

      계층 구조 잘 챙길것

      사용하기 전에 무조건 이 구조를 생각하면서 짜야한다

      Entity 클래스 
      @Getter
@Entity
@Table(name = "users")
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(length = 50, nullable = false)
    private String name;
    @Column(unique = true, nullable = false)
    private String email;
    private String address;

    public User(String name, String email, String address) {
        this.name = name;
        this.email = email;
        this.address = address;
    }
    
    // 더티 체킹용
    public void update(String name, String email, String address) {
        this.name = name;
        this.email = email;
        this.address = address;
    }
}
      ⚠️
      User 클래스로 객체를 만드려면 생성자가 필요하며, User의 필드인 id는 DB에서 자동으로 생성되는 값이므로, id를 제외한 나머지 필드들만 포함한 생성자가 필요
      Service 클래스 
      @Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;

		// 저장
    @Transactional
    public void save() {
        User user = new User("홍길동", "asd@gmail.com", "서울");
        userRepository.save(user);
    }

		// 단 건 조회
    @Transactional(readOnly = true)
    public void getOne() {
        User user = userRepository.findById(1L).orElseThrow(
                () -> new IllegalStateException("존재하지 않는 유저입니다.")
        );
    }

		// 전체 조회
    @Transactional(readOnly = true)
    public void getAll() {
        List<User> all = userRepository.findAll();
    }

		// 삭제
    @Transactional
    public void delete() {
        boolean existence = userRepository.existsById(1L);
        // 존재하지 않는다면
        if (!existence) {
            throw new IllegalStateException("존재하지 않는 유저입니다.");
        }

        // 존재한다면
        userRepository.deleteById(1L);
    }

    // 더티 체킹
    @Transactional
    public void update() {
        User user = userRepository.findById(1L).orElseThrow(
                () -> new IllegalStateException("존재하지 않는 유저입니다.")
        );
        user.update("새로운 이름", "new-email@naver.com", "경기도");
    }
}
      Repository 클래스 
      public interface UserRepository extends JpaRepository<User, Long> {
}
      더티체킹 과정 (update 주목)
      1. @Transactional라는 어노테이션 붙이고 트랜잭션 내에서 findById 등으로 Entity조회 시, JPA의 영속성 컨텍스트가 이 객체를 관리된다
      2. 메모리에는 조회한 Entity의 최초의 상태를 스냅샷(Snapshot)으로 복사 해둔다
      3. 조회된 Entity를 update같은 함수로 객체를 수정한다
      4. @Transactional이 붙은 메서드가 정상 종료되어 트랜잭션 커밋이 일어나는 시점에, JPA는 내부적으로 플러시(Flush)
      5. 상태가 변경된 것(Dirty)이 감지되면 JPA가 알아서 UPDATE SQL을 만들어 DB에 전송
      더티체킹 주의할 점
      1. new User() 시에는 동작 안함 (단, 데이터 접근하는 Repository로 호출 시 작동)
      2. @Transactional 트랜잭션 필수 (정상 종료 시에만 작동, 오류 시 동작 안함)
