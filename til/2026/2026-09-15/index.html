      [TIL] 단기심화 9기 12일차

      2026년 9월 15일

      뭔가 집중이 잘 안되고 있다. 왜지?

      오늘은 뭔가 집중이 잘 안되는 하루였다

      내일부터 프로젝트 발제 들어가는데 오늘은 설렁설렁 쉬면서 앉아있는 느낌이 들었다

      듣기로는 발제 내용이 웹소켓에 관한 것 이라는데 프로젝트 발제가 두렵다

      실시간 강의가 있었고 컴퓨터공학 분반은 오후 3시, Spring 분반은 오후 4시에 있었다



      1. DNS — 이름을 주소로 바꾼다

      • IP = 건물 주소, 포트 = 몇 동 몇 호 둘 다 있어야 목적지를 찾음

      • api.game.com 같은 도메인 네임은 숫자 IP를 사람이 쓰기 쉽게 감싼 것 (보안 이슈도 있어 숫자 IP를 그대로 노출하지 않음)

      • 클라이언트 → DNS 리졸버(통신사/8.8.8.8 등)에 질의 → IP 응답

      • 매번 질의하면 비효율이므로 로컬 캐시에 TTL 동안 저장함

      • 로컬 개발 시 localhost:8080의 8080은 Tomcat 기본 포트임

      장애 신호: UnknownHostException → 코드는 멀쩡한데 이름이 안 풀린 것 도메인 오타나 DNS 설정부터 의심해야 함



      2. TCP — 연결을 맺는다 (3-way Handshake) 

      클라이언트 --- SYN (연결할게요) ---> 서버
클라이언트 <-- SYN-ACK (좋아요, 나도) --- 서버
클라이언트 --- ACK (확인, 보냅니다) ---> 서버
      • 왕복 1.5회 = 연결 비용
      • TCP는 상태(state)를 가진 연결임 전화 통화처럼 한번 연결되면 그 상태가 유지됨
      • ⚠️ 흔한 오해: “HTTP가 stateless니까 TCP가 아니다"는 틀린 생각임 HTTP는 상태 있는 TCP 연결 위에서 도는 무상태 프로토콜임

      TCP vs UDP

      구분TCPUDP
      순서 보장OX
      재전송O (누락 자동 감지 후 재요청)X
      속도상대적으로 느림빠름
      용도웹서버, 상점, 랭킹실시간 위치, 음성, 전투 동기화

      TCP가 느린 이유는 순서를 정렬하고 누락을 검증하는 작업이 추가로 들기 때문임 — 외울 필요 없이 원리로 이해하면 됨

      Keep-alive

      • HTTP/1.0 초기: 요청마다 handshake → 응답 → 연결 종료를 반복 (비효율적)
      • HTTP/1.1 기본값: handshake는 한 번만 하고, 그 연결(파이프) 위로 여러 요청을 흘려보냄
      • Tomcat은 대기시간이나 연결당 요청 수(기본 100)를 넘기면 연결을 닫고, 클라이언트는 커넥션 풀로 재사용함



      3. TLS / HTTPS

      TCP와 HTTP 사이에 끼워 넣는 보안 계층 도청·위조·변조를 방지함

      1. ClientHello   — 쓸 수 있는 암호화 방식 목록, 난수
2. ServerHello   — 방식 선택 + 인증서(공개키)
3. 인증서 검증(CA 서명) → 키 교환 → 세션키 합의
4. 이후 모든 HTTP 텍스트는 세션키로 암/복호화
      • 인증서는 CA(인증기관)가 서명한 서버 신분증임 OS/브라우저가 믿는 CA 목록으로 검증함
      • TCP(1.5 RTT) + TLS(1~2 RTT) ≈ 연결 하나에 3.5회 왕복 연결이 비쌀수록 keep-alive가 더 중요해짐

      실무 디테일: TLS 핸드셰이크는 보통 Spring Boot가 도는 서버가 직접 하지 않음 로드밸런서/프록시가 앞단에서 TLS를 벗겨주고, 프록시와 서버 간은 이미 검증된 내부망이라 평문 HTTP로 통신하는 경우가 많음 http/https 구분은 애플리케이션 코드가 아니라 인프라의 몫임



      4. HTTP는 결국 “텍스트"다 

      POST /api/users HTTP/1.1
Host: api.game.com
Content-Type: application/json
Authorization: Bearer eyJ...

{"nickname":"용사","level":1}
      • 요청 라인(메서드 + 경로) / 헤더(부가정보) / 바디(실제 데이터)로 구성됨
      • 메시지 경계는 빈 줄 + Content-Length로 정해짐 TCP는 바이트 배열일 뿐 메시지 경계를 모름

      캡슐화 (내려갈수록 헤더가 겹겹이 붙는다)

      계층하는 일
      애플리케이션HTTP 텍스트 생성 (요청라인·헤더·바디)
      TCP세그먼트로 자르고 TCP 헤더(포트·순번) 부착
      IPIP 헤더(목적지 주소) 부착
      이더넷프레임 헤더(MAC 주소) 부착 → 전기 신호 송신

      받는 쪽은 역순으로 하나씩 벗김 Spring 코드는 맨 안쪽 HTTP 텍스트만 다룰 뿐, 나머지 캡슐화/역캡슐화는 커널과 네트워크 장비가 알아서 처리함 포트 8080 소켓 버퍼의 바이트를 Tomcat이 read()하는 순간 비로소 ‘HTTP 요청’이 됨

      메서드 / 상태 코드

      메서드의미
      GET조회 — 바디 없음, 캐시 가능
      POST생성/행위 — 바디 있음
      PUT/PATCH수정 (전체/부분)
      DELETE삭제
      코드대의미
      200/201성공 / 생성 성공
      400클라이언트 잘못 (형식·검증)
      401/403로그인 안 됨 / 권한 없음
      404없는 리소스
      409상태 충돌
      500서버 잘못 (버그)

      500은 내 잘못, 400은 클라이언트 잘못 — 이 구분이 새벽 알람의 성격을 가름



      5. Stateless와 인증 토큰

      서버는 요청이 끝나면 그 요청에 대한 정보를 메모리에 들고 있지 않음 그래서 매 요청마다 Authorization: Bearer <토큰>을 들고 가서 “내가 누구인지"를 매번 증명해야 함 클라이언트 객체는 앱이 살아있는 동안 유지되지만, 서버의 요청 컨텍스트는 응답과 함께 사라짐



      6. 서버 안에서 — Tomcat, 스레드풀, 3계층 

      요청들(동시에) → Tomcat(8080 리슨, accept())
  → 스레드 풀(기본 200개) → 스레드 하나가 요청 하나를 끝까지 처리
      • 스레드 하나가 요청을 처리하는 동안 블로킹(동기) 상태 — DB 응답을 기다리는 동안 다른 일을 못 함
      • 200개가 전부 DB를 기다리면 201번째 요청은 큐에서 대기함
      • 물리 스레드 수는 CPU 코어 수 × 1.5 정도로 한정 → 무한정 늘릴 수 없음
      • 그래서 서버 한 대가 아니라 여러 대로 늘리는 스케일아웃이 등장함

      라우팅 → 3계층 

      GET /api/users/42
  → DispatcherServlet (경로 매칭)
  → Controller (HTTP를 벗겨 자바 객체로)
  → Service (규칙 실행: 존재 확인·권한·계산)
  → Repository (DB에 SELECT/UPDATE)
  → 역순으로 응답, 다시 JSON으로



      7. 시간은 어디서 쓰이는가

      구간대략비고
      DNS 조회0~50ms캐시되면 0
      TCP+TLS 핸드셰이크1~3.5 RTTkeep-alive로 재사용
      서버 코드 (Controller~Service)1ms 미만정상이면 병목 드묾
      DB 조회1~수백ms인덱스 유무가 가름
      네트워크 왕복(RTT)물리 거리서울↔서울 수ms, 서울↔미국 ≈150ms

      데이터는 빛의 속도(광통신)로 이동하지만, 물리적 거리 자체가 멀어서 서울↔미국 왕복은 150ms가 걸림 네트워크 왕복이 느린 건 물리적 한계(우주 차원의 문제), 서버 코드나 DB 조회가 느린 건 개발자의 문제임



      8. 장애는 계층별로 진단한다

      증상끊긴 계층의심할 것
      UnknownHostExceptionDNS도메인 오타, DNS 설정
      Connection refusedTCP서버 미기동, 포트 오류
      Timeout네트워크/서버방화벽, 서버가 오래 붙잡고 있음
      4xxHTTP (클라이언트)경로·바디·토큰 확인
      5xx서버 코드스택트레이스 → 로그

      에러는 ‘어느 계층’인지를 먼저 말해줌 — 거기부터 확인해야 함

      1. 세션(Session) vs JWT — 문제는 “서버가 여러 대일 때” 시작된다

      세션 기반 인증의 한계 

      클라이언트 --[세션]-- 인증 서버 --- 유저DB
                채팅 / 배달 / 알림 / 주문 / 가게 / 고객센터 / 리뷰 ...
      • 로그인하면 서버가 세션을 만들어 세션 저장소에 보관하고, 클라이언트는 세션 ID만 들고 다님
      • 문제는 서비스가 여러 서버(마이크로서비스)로 분리되는 순간임 인증 서버가 들고 있는 세션 저장소를 다른 서비스(예: 가게 서비스)는 알지 못함
      • 그래서 세션을 다른 서비스에서도 쓰려면, 그 서비스도 인증 서버의 세션 저장소를 매번 조회하러 가야 함 → 서비스 간 결합도가 높아지고, 신규 서비스를 추가할 때마다 기존 인증 인프라에 의존해야 함

      예시: “B마트"라는 신규 서비스를 새로 런칭했다고 하자 세션 방식이면 B마트 서버도 기존 인증 서버의 세션 저장소를 계속 바라봐야 유저를 식별할 수 있음 서비스가 늘어날수록 이 의존이 반복됨

      JWT가 해결하는 것

      • JWT(JSON Web Token)는 토큰 자체에 사용자 데이터를 담음
      { "id": 1, "name": "honggildong", "age": 14 }
      • 토큰 안에 필요한 정보가 이미 들어있기 때문에(=stateless), 어떤 서비스로 요청이 가든 별도의 세션 저장소 조회 없이 토큰 서명만 검증하면 그 자리에서 바로 사용자를 식별할 수 있음
      • 그래서 채팅/배달/알림/주문/가게/고객센터/리뷰뿐 아니라 나중에 추가되는 B마트, C마트 같은 신규 서비스도 인증 서버에 매번 의존하지 않고 독립적으로 유저를 인증할 수 있음
      • 이게 마이크로서비스 아키텍처(MSA)에서 JWT가 세션보다 유리한 핵심 이유임

      한 줄 요약

      SessionJWT
      사용자 정보 위치서버(세션 저장소)토큰 자체
      서버 확장 시세션 저장소 공유/조회 필요 (결합↑)토큰만 검증하면 됨 (독립적)
      적합한 구조단일 서버 / 소규모MSA(여러 서비스로 분리된 구조)



      2. JPA 영속성 컨텍스트 — “같은 데이터는 같은 객체여야 한다”

      문제 상황: JPA 없이 생 DB 호출을 하면 

      // JPA를 쓰지 않고, 생으로 DB 호출을 했을 때
Member m1 = db.exec("SELECT * FROM Members WHERE id = 1;");
Member m2 = db.exec("SELECT * FROM Members WHERE id = 1;");

// 메모리 주소 비교
System.out.println(m1 == m2); // false
      • 같은 id로 같은 데이터를 두 번 조회했는데도 m1 == m2는 false임
      • 이유는 ==가 메모리 주소(참조) 비교이기 때문 — 매번 새로운 객체가 생성되니 당연한 결과임
      • 하지만 이건 우리가 원하는 동작이 아님 “같은 id로 조회한 같은 데이터인데 왜 다른 객체야?“라는 게 상식적인 기대이고, 객체지향(Spring)이 원하는 동작도 “같은 객체는 같은 참조로 다뤄야 한다"는 것임
      • DB(관계형, 상태 중심)와 자바(객체지향)는 애초에 사고방식이 다름 — 이 간극을 **패러다임 불일치(paradigm mismatch)**라고 부름

      JPA의 해결책: 영속성 컨텍스트(1차 캐시)

      영속성 컨텍스트는 트랜잭션(@Transactional) 내에서 데이터베이스를 한 번이라도 갔다 온 엔티티를 관리하는 논리적인 공간(메모리 공간)임 효율적인 작업을 위해 도구와 재료를 미리 꺼내놓는 ‘작업대’와 같음 JPA는 이 작업대 위에서 엔티티들을 관리하다가, 트랜잭션이 끝나면 최종 결과물만 DB에 반영함

      // 같은 트랜잭션 내에서
// Member를 저장
Member savedMember = memberRepository.save(newMember);

// ...

// 위에서 저장한 Member의 id로 Member를 조회
Member member = memberRepository.findById(savedMember.getId())
    .orElseThrow(() -> new IllegalStateException("존재하지 않는 멤버입니다."));

// 여기서 savedMember는 영속성 컨텍스트에 저장되고,
// 그 이후에 동일한 엔티티를 조회하면 DB를 조회하지 않고 캐시의 엔티티를 반환한다

      동작 원리를 Map으로 비유하면:

      // 영속성 컨텍스트 ≈ Map<PK, Entity>
Map<Long, Member> persistenceContext = new HashMap<>();
persistenceContext.put(savedMember.getId(), savedMember);   // save 시점에 등록

Member member = persistenceContext.get(savedMember.getId()); // findById 시점

savedMember == member; // true !!
      • save() 시점에 영속성 컨텍스트(1차 캐시)에 id → entity로 등록해둠
      • 이후 같은 트랜잭션 안에서 같은 id로 다시 조회하면, DB를 다시 왕복하지 않고 캐시에 있던 그 객체(참조)를 그대로 반환함
      • 그래서 savedMember == member는 true가 됨 — 우리가 원했던, 상식적으로 “같은 데이터는 같은 객체"인 동작이 완성됨
      • 부수 효과로 DB 왕복 횟수도 줄어듦 (불필요한 쿼리 최적화)

      트랜잭션 vs 영속성 컨텍스트

      개념정의
      트랜잭션여러 작업을 하나의 단위로 묶어 모두 성공하거나 모두 실패하게 하는 것
      영속성 컨텍스트트랜잭션(@Transactional) 내에서 DB를 한 번이라도 갔다 온 엔티티를 관리하는 1차 캐시
