      2026년 9월 18일

      배운 걸 까먹고 분명 봤는데

      데이터 관리 방법

      서버의 메모리

      같은 데이터라도 어디에 두느냐에 따라 속도와 수명이 달라진다

      서버가 느려지거나 멈추는 원인의 상당수는 메모리에서 시작된다

      동시성 버그는 여럿이 함께 쓰는 메모리에서만 생긴다

      데이터가 놓이는 3가지 구역

      JVM 메모리 (다른 곳에서도 동작은 비슷함)

      스택에서는 따로 쓰기때문에 상관없지만 객체가 생성되는 힙에서 동시성 버그가 일어난다.

      각 장소에서의 에러

      스택: StackOverflowError 힙: OutOfMemoryError

      GC의 원리

      참조가 풀린 객체들을 정리한다

      GC 처리과정

      3가지 다 O(n)의 결과값을 가지지만 O(logN)이 아닌이상 효율적이라고 볼 순 없다

      GC가 발생하는 시간

      GC 힙을 나이순으로 나눔

      객체가 만들어 졌을때 바로 참조 끊겼는지 확인하고 S0나 S1으로 넘김

      이후 더 오래 살아남으면 Old로 넘김

      그리고 Young 힙에 들어있는 객체들은 Old 보다 자주 GC에게 검사받음

      static은 바로 Old 힙에 넣음

      주의사항

      이렇게 사용하면 힙이 터진다

      데이터는 어디에 두는가

      DB에 두는 이유는 여러개의 서버 컴퓨터가 원자성을 가진 데이터를 보장받기위해 사용된다

      적합한 DB 3가지

      적재적소에 DB를 다르게 사용할 줄 알아야 하는 이유

      서버의 힙: 서버 메모리에 바로 보관됨 Redis: DB 메모리에 보관됨 MySQL: DB 디스크에 보관됨

      캐시 레이어를 두는 이유

      I/O가 많이 일어나기 때문에 Redis를 무조권 둘 수 밖에 없음

      먼저 Redis에 캐시 조회해보고 캐시 미스가 났으면 DB에서 조회후 다시 Redis에 저장해놓음

      만약 DB에 제대로 저장이 안되면 대형사고가 일어나기 때문에 DB저장을 한번씩 꼭 해줘야 한다.

      캐시에서 어려운 건 넣기가 아니라 지우기

      Redis에서 쓰는곳에 따른 자료구조 형식

      요약 및 정리

      요약 정리

      테스트 코드

      테스트하기 쉽게 만든 코드가 코드 품질이 높을 확률이 높다

      배포단계에서의 안정성을 보장해준다 CI: 자동 테스트(검증) CD: 자동 배포

      시간이 지날 수록 테스트 해야 하는 기능들이 많아진다

      회귀 테스트: 우리가 뭔가 고쳣을때 망가지지 않게 하는것

      테스트의 종류

      1. 단위 테스트
      • 테스트가 매우 빠르게 실행된다 (작게작게)
      1. 통합 테스트
      • 실제 인프라(의존성)도 포함된다 (데이터 흐름을 검증)

      테스트가 없으면 무섭다!
